# Sic Bo — протокол модели

**Роль документа: истина для смысла. Машиночитаемая часть — `schema.json`.**
Где проза расходится со схемой, действует схема (Регламент §1).

| | |
|---|---|
| Модель | `sicbo` |
| Версия SDK | `@playtagon/model-sdk` 0.2.0 |
| Режим RNG | `fairness` (провабли-фэйр) |
| Раундов на ставку | ровно один; раунд одношаговый, под-раундов нет |
| Точка входа | `model/playtagon.ts`, экспорт `createModel` (повтор `schema.json#entry`) |

---

## 1 · Механика в одном абзаце

Игрок расставляет фишки по зонам стола Sic Bo и бросает три шестигранные
кости. Случай решает одно — какие три грани выпали; всё остальное выводится из
броска детерминированно. Каждая занятая зона рассчитывается **независимо**: один
бросок может выиграть сразу несколько зон (3,3,3 выигрывает и `triple_any`, и
`triple_3`, и `double_3` — это канон игры, а не двойная выплата за одно и то
же). Выигравшая зона возвращает ставку вместе с выигрышем, то есть множитель
возврата равен коэффициенту плюс единица; проигравшая зона не возвращает
ничего. Итог раунда — сумма выплат по всем выигравшим зонам.

## 2 · Порядок сообщений

```
клиент                     платформа + модель
  │
  │ ── init ───────────────▶ платформа зовёт model.init()
  │ ◀───────────── initData  { betTypes, payouts, history }
  │
  │ ── play {gameRequest} ─▶ платформа зовёт model.play({roundType, gameRequest, rng, …})
  │ ◀───────────── playData  { roll, bets, wins, totalBet, totalWin, category }
  │                          (клиенту уходит проекция: bet, win, roundComplete, playData)
  │
  │ ── verify {roundId} ───▶ роль ПЛАТФОРМЫ: по roundId она восстанавливает
  │                          зафиксированный буфер RNG и зовёт model.verify({rng}).
  │                          roundId — слово платформы; модель его не видит.
  │ ◀──────────── verifyData { roll }
```

Порядковые правила и их природа:

- **клиент обязан вызвать `init` до первого `play`** — иначе он не знает состава
  зон и коэффициентов для подписей. Это **соглашение, а не машинное
  принуждение**: модель порядок **не проверяет** и не может — состояния
  «инициализирован» у неё нет;
- `roundType` конверта **игнорируется**: модель не объявляет `roundTypes`, все
  раунды считаются одинаково. При отсутствии поля платформа подставляет
  `"main"`; на расчёт это не влияет;
- **резолв `roundId` → буфер RNG делает платформа**, а не `model.verify()`
  (Регламент §9.2). Модель получает уже готовый `rng`.

## 3 · `init`: источник значений ручек и единицы измерения

**Откуда берутся значения.** Модель не читает `config.json` и не хранит значений
в коде. Платформа на каждую сессию зовёт `createModel(values)` со значениями
ручек действующей версии конфига; фабрика проверяет их против `schema.json#knobs`
и собирает таблицу коэффициентов, по которой считается раунд. Два экземпляра с
разными `values` живут в одном процессе одновременно.

| Поле `initData` | Что это | Какая ручка стоит за ним |
|---|---|---|
| `betTypes` | все 50 зон стола, по которым клиент строит разметку | — (состав задан механикой трёх костей, конфигом не меняется) |
| `payouts` | коэффициент (профит, без возврата ставки) по каждой зоне | `total_S` ← `total_payouts.S`; `triple_N` ← `triple_specific_payout`; `triple_any` ← `triple_any_payout`; `double_N` ← `double_payout`; `combo_NN` ← `combo_payout`; `small`/`big`/`single_N` — константы механики (см. §5) |
| `history` | всегда пустой массив | — (fairness запрещает cross-round context; историю ведёт клиент) |

**Единицы измерения.**

- `bet`, `win`, `amount`, `payout`, `totalBet`, `totalWin` — целые в **младших
  единицах валюты**. Деноминацию задаёт РГС; модель её не знает и не
  интерпретирует;
- коэффициенты в `payouts` — **профит без возврата ставки**: зона с
  коэффициентом 6 возвращает `amount × 7`. Клиент показывает их как «6:1»;
- грани `roll` — целые 1…6; `category.total` — их сумма, 3…18.

## 4 · `play`: инварианты и ошибки раунда

**Инварианты** (каждый проверяем):

1. **Ровно три обращения к RNG на раунд** — `rng.getInt(1, 6)` трижды подряд,
   в порядке костей. Больше или меньше не бывает ни при каком запросе.
2. **Валидация до розыгрыша.** Отвергнутый раунд **не тратит ни одного числа**
   из буфера RNG: сначала все проверки, потом первый `getInt`.
3. **Эхо полей запроса.** `playData.bets` — список ставок запроса без изменений.
4. **Каждая зона считается независимо.** Один бросок может выиграть несколько
   зон; `wins` содержит запись на каждую выигравшую зону и не содержит записей
   на проигравшие.
5. **Формула выплаты зоны:** `payout = amount × (коэффициент + 1)` для
   выигравшей зоны, где коэффициент — значение действующего конфига.
   Для `single_N` — особый случай, см. §5. **Округления нет**: все величины
   целые, произведение целых целое.
6. **Равенство денежных дублей.** `PlayResult.bet === playData.totalBet`,
   `PlayResult.win === playData.totalWin`,
   `totalWin === Σ wins[].payout`, `totalBet === Σ bets[].amount`.
7. **`replayData` тождественно `playData`** — раунд одношаговый, срез для
   реплея совпадает с данными раунда.
8. **`roundComplete` всегда `true`**, `roundContext` и `globalContext` всегда
   `null`.

**Ошибки раунда — полный список причин отказа.** Все они бросают
`RequestValidationError` (класс — в §8), все проверяются **до** розыгрыша, и все
нарушения собираются **в один список**, а не бросаются по одному:

| Причина | Пример |
|---|---|
| запрос не объект | `null`, массив, строка |
| отсутствует обязательное поле `bets` | `{}` |
| необъявленное поле в запросе | `{bets: […], cheat: true}` |
| `bets` не массив | `{bets: {…}}` |
| пустой список ставок | `{bets: []}` — объявлен `minItems: 1` |
| ставок больше 50 | зон на столе всего 50, дубли запрещены |
| элемент `bets` не объект | `{bets: [42]}` |
| в ставке нет `type` или `amount` | `{bets: [{type: "small"}]}` |
| необъявленное поле внутри ставки | `{bets: [{type, amount, multiplier}]}` |
| `type` не строка либо не из перечня 50 зон | `combo_99` |
| **дубль зоны** в одном раунде | две записи `small` — фишки одной зоны складывает клиент |
| `amount` не число, `NaN` или `Infinity` | `"100"`, `NaN` |
| `amount` нецелое | `10.5` |
| **`amount` меньше 1** | `0` и любое отрицательное — см. «Границы ставок» |
| `amount` выше `Number.MAX_SAFE_INTEGER` | потолок представимости |

**Границы из ручек.** Полей запроса, чьи границы задаются ручками, у этой модели
**нет**: ручки управляют только коэффициентами выплат, а состав зон и пределы
ставки от конфига не зависят. Поэтому секция `request` не содержит ни одной
пометки `x-bounds`, и проверять против действующего конфига в `play()` нечего.

**Ответ модели всегда проходит её собственную схему.** Канала «ответ-ошибка» не
существует: модель либо возвращает `PlayResult`, проходящий `schema.json`, либо
бросает исключение. Третьего состояния нет.

## 5 · Краевые случаи механики

Всё, где читатель может ошибиться в «очевидном».

**`small` и `big` проигрывают на тройке, даже когда сумма в диапазоне.**
Бросок 2,2,2 даёт сумму 6 — это диапазон `small` (4…10), — но `small` **не
платит**: любая тройка бьёт обе зоны. Это край дома, а не дефект: именно на нём
стоит преимущество заведения в зонах, которые иначе платили бы почти честные
48.61 % шанса при коэффициенте 1:1.

**`double_N` выигрывает и на тройке.** Три одинаковые грани содержат и пару,
поэтому 3,3,3 оплачивает `double_3`. Обратное неверно: пара тройкой не является.

**`combo_NN` требует ОБЕ разные грани.** Бросок 2,2,2 **не** оплачивает
`combo_22` — такой зоны не существует: комбинации строятся только из двух
**разных** граней, их ровно 15. Реализация снимает первую грань из броска и ищет
вторую в остатке, поэтому «комбинация с самой собой» не проходит.

**`single_N` платит по ЧИСЛУ совпадений, а не фиксированным коэффициентом.**
Одно совпадение возвращает 2×, два — 3×, три — 4× ставки. Множитель не
выводится из таблицы коэффициентов одним умножением, поэтому `payouts.single_N`
равен 1 и означает «база при одном совпадении».

**Коэффициенты, НЕ настраиваемые конфигом.** `small`, `big` (1:1) и `single_N`
остались константами исходного кода и ручками **не являются**. Причина
математическая: их шаг целым числом переводит RTP через 100 % — `small`/`big`
с 97.22 % прыгнули бы на 145.83 %, `single_N` с 92.13 % на 176.39 %, — а дробная
выплата означала бы округление, которого в этой математике нет. Настраиваются
они **только правкой исходников** (`model/math.ts`) с перевыпуском версии
модели.

**Единого RTP у игры нет.** Он зависит от того, на какие зоны игрок поставил:
при дефолтных коэффициентах разброс по зонам — **81.02 % … 97.22 %** (худшие
`total_9`/`total_12`, лучшие `small`/`big`/`combo_*`). Поэтому ручки с
`x-role: "target-rtp"` в схеме **нет**, и платформа получает
`declaredRtp: null` — законное состояние по Регламенту 5.3.1: заявлять
одно число было бы неправдой. Судить математику следует по трекеру симуляций,
который кладёт рядом с измеренным RTP теоретический, выведенный из фактических
ставок раунда.

## 6 · Провабли-фэйр

- **Режим** — `rngMode: "fairness"`. РГС поставляет зафиксированный
  детерминированный буфер случайных чисел по `(serverSeed, clientSeed, nonce)`;
  игрок может пересчитать бросок сам.
- **Где разыгрывается случайность** — целиком в первом (единственном)
  под-раунде: три `rng.getInt(1, 6)` подряд. Cross-round состояния нет,
  `globalContext` всегда `null`, как того требует режим.
- **Паритет траты RNG.** `verify()` потребляет буфер **идентично** `play()`:
  те же три вызова `getInt(1, 6)` в том же порядке. Иначе потоки разошлись бы и
  проверка ничего не доказывала бы.
- **Идемпотентность.** `verify()` не меняет состояния и на одном и том же буфере
  возвращает один и тот же результат сколько угодно раз.
- **Связка `roundId` ↔ буфер RNG.** Клиент шлёт платформе `verify {roundId}`.
  **Платформа** хранит буфер каждого раунда (сид сессии плюс позиция потока) и
  восстанавливает его перемоткой, после чего зовёт `model.verify({rng})`.
  `roundId` — слово платформы: модель его не получает и о нём не знает.
- **Что обязано совпадать.** `verifyData.roll` **тождественно равен**
  `playData.roll` того же раунда — все три грани и их порядок.

## 7 · Чего у модели нет

- **`roundContext`** — всегда `null`. Раунд одношаговый: между запросами
  хранить нечего.
- **`globalContext`** — всегда `null`. Запрещён режимом `fairness`.
- **Под-раундов** нет: один `play` — один законченный раунд,
  `roundComplete: true` всегда.
- **Бонусных режимов, фриспинов, прогрессивных джекпотов** нет.
- **`roundTypes`** модель не объявляет; значение `roundType` из конверта
  **игнорируется** (платформа подставит `"main"`).
- **Истории раундов на сервере нет** — `initData.history` всегда пустой массив.
  Ленту раундов ведёт клиент.
- **Ограничений ставок модель не объявляет и не проверяет.** Продуктовые лимиты
  (минимум на зону, максимум на раунд, номиналы фишек, баланс) — зона
  РГС/оператора; см. «Границы ставок».
- **Ручки заявленного RTP нет** (`x-role: "target-rtp"` отсутствует) — см. §5.
- **Секретных ручек нет**: все пять ручек несекретны, и ни одна не запрещена к
  показу. Коэффициенты по определению публичны — они напечатаны на столе.

## 8 · Типы исключений модели

Секции ошибок в `PlayResult` не существует — ошибка модели это **типизированное
исключение**. Классы экспортируются из точки входа рядом с фабрикой; узнавание —
по `err.name` (через границу бандла классы не переносятся, `instanceof` не
работает).

| `err.name` | Кто бросает | Когда | Поля |
|---|---|---|---|
| `ConfigValidationError` | `createModel(values)` | `values` не проходят `schema.json#knobs`: неверный тип, значение вне `min`/`max`, нецелое у `int`, отсутствующая ручка, необъявленная ручка, нарушение формы составной ручки `total_payouts` (лишний/отсутствующий ключ), нарушение инварианта смысла (коэффициент уводит RTP зоны выше 100 %) | `message`, `violations: string[]` — **все** нарушения сразу; для составной ручки нарушение называет путь до элемента (`total_payouts.9`) |
| `RequestValidationError` | `play()`, **до розыгрыша** | запрос не проходит секцию `request`: полный перечень причин — в §4 | `message`, `violations: string[]` — **все** нарушения сразу, каждое с путём (`bets[2].amount`) |
| любое другое | — | сбой математики: модель в таком состоянии считать не имеет права | — |

Мапинг исключений в HTTP-ответы (`422 MODEL_CONFIG_INVALID`,
`400 MODEL_REQUEST_INVALID`, `500 MODEL_PLAY_FAILED`) — **конвенция платформы,
а не модели**: модель отвечает только за тип исключения и его содержимое.

`buildModel(values)` — вторая половина пары конвенции (Регламент §11.1) —
`ConfigValidationError` **не бросает вовсе**: она собирает модель из
заведомо-валидных значений без чтения схемы и без валидации, и её вызывает
только генерируемый bake-адаптер платформы.

## 9 · Границы ставок

**Продуктовые границы объявляет РГС/оператор, а не модель** (Регламент 5.6).
Валюты, номиналы фишек, минимум и максимум стола, доступный баланс — всё это
живёт вне бандла модели и меняется без её перевыпуска. В проде профиль ставок
выдаёт РГС оператора (`bet_config`), в DEV — платформа. Модель этого профиля не
видит и в `schema.json` его не объявляет.

Модель проверяет **только технические пределы** поля `amount` каждой ставки —
границы, за которыми ломается сама арифметика:

| Предел | Значение | Почему |
|---|---|---|
| минимум | **1** (строго больше нуля) | нулевая и отрицательная ставка отвергают раунд: до конверсии отрицательная ставка доезжала до расчёта и давала отрицательную выплату в денежном контуре |
| шаг | целое число | все денежные величины — целые в младших единицах; дробная ставка даёт дробную выплату, которой в этой математике нет |
| потолок | **9007199254740991** (`Number.MAX_SAFE_INTEGER`) | выше него целочисленность выигрыша не гарантируется double |

Обе границы **включительны**: `amount = 1` принимается, `amount = 0` — нет.
Запрос с любой ставкой внутри технических пределов для модели валиден —
продуктовые границы модель не проверяет вовсе.

Отдельно: **баланс модель не проверяет**. Достаточность средств — обязанность
РГС, который списывает ставку и начисляет выигрыш.
