# Протокол модели «Дайс»

Истина для смысла (§2.1). Машиночитаемая часть контракта — `schema.json`; здесь
описано то, что схема выразить не может: порядок сообщений, семантика полей и
инварианты, связывающие поля между собой.

- Модель: `dice`, SDK `@playtagon/model-sdk` 0.2.0
- Режим RNG: `fairness` (провабли-фэйр)
- Раундов на ставку: один. `roundComplete` всегда `true`, под-раундов нет.
- Точка входа: `model/playtagon.ts` (исходная), фабрика `createModel(values) → IModel` —
  объявлена в `schema.json#entry`. Бандл едет **исходниками SDK-канона** (§8.2:
  `model/` + `scenarios/` + `simulations/` + манифесты); исполняемую форму
  (`dist/index.mjs`) собирает платформа при приёме, в бандле она не едет.
  Форма объявления `{module, export}` закреплена приёмом devРГС (source-intake);
  нормирование имени адаптера регламентом (Д-6) — за штабом.
- Двери модели две: `model/index.ts` — SDK-канонический default-export `IModel`
  для дев-контура (Debug RGS, симуляции, `playtagon check`), экземпляр от
  default-значений `schema.json#knobs`; `model/playtagon.ts` — платформенный
  вход, только фабрика. Конвенция фабрики этим не ослабляется: платформа
  исполняет исключительно `createModel(values)`.

## 1. Механика в одном абзаце

Игрок выбирает порог `target` и направление `condition`. Сервер бросает равномерное
целое `roll` на отрезке `[0, 9999]`. Выигрыш наступает, если `roll > target` при
`condition = "over"` либо `roll < target` при `condition = "under"`. Множитель
известен до броска и равен `rtp / winChance`. Равенство `roll == target` —
проигрыш при обоих направлениях (см. §5).

## 2. Порядок сообщений

```
клиент                         РГС + модель
  |                                 |
  |------------- init ------------->|   один раз при открытии игры
  |<---- initData + bets + PF -------|   model.init()
  |                                 |
  |------ play {target,             |   на каждую ставку
  |             condition, bet} --->|
  |<---- playData + balance --------|   model.play(), ровно один розыгрыш RNG
  |                                 |
  |------ verify {roundId} -------->|   по желанию игрока, в любой момент после раунда
  |<---- verifyData {roll} ---------|   model.verify()
```

Порядок жёсткий: `init` предшествует первому `play`. Без `init` клиент не знает
границ цели и `rtp`, а значит не может показать множитель до броска.

`verify` не входит в игровой цикл и не меняет состояние. Он может быть вызван
сколько угодно раз и обязан каждый раз возвращать один и тот же `roll`.

## 3. init

### Откуда берутся значения ручек — конвенция фабрики (§1.5.1)

Модель создаётся фабрикой: `createModel(values) → IModel`, где `values` —
значения ручек действующего конфига, переданные **аргументом при старте
сессии**. Это единственный вход значений в математику:

- модель **не читает файлов**: ни `config.json`, ни что-либо ещё — ни на
  загрузке модуля, ни в рантайме (собственная `schema.json` — объявление,
  принадлежащее модели, — читается лениво для валидации);
- `config.json` в бандле — объявление значений и метаданных контролов для
  платформы (§2.4); платформа импортирует его в строку `model_configs`, и до
  модели значения доезжают только через аргумент фабрики;
- фабрика валидирует `values` против `knobs` собственной схемы: тип, `min`/`max`,
  присутствие каждой объявленной ручки, отсутствие необъявленных, кросс-инварианты
  (`target_min < target_max`, `default_target` внутри). Любое нарушение —
  `ConfigValidationError` со списком всех нарушений; **тихих дефолтов нет** (§5.1);
- каждый вызов фабрики возвращает независимый экземпляр: один процесс держит
  параллельные сессии с разными `values`, глобального состояния у модели нет.

Модель отдаёт `initData` — снимок действующих ручек (§1.5), по которому клиент
настраивает интерфейс:

| Поле | Смысл |
|---|---|
| `rollMin`, `rollMax` | границы броска, всегда `0` и `9999` — свойство механики, не ручка |
| `targetMin`, `targetMax` | границы цели, значения ручек `target_min` / `target_max` |
| `defaultTarget` | цель при открытии, значение ручки `default_target` |
| `rtp` | значение ручки `rtp`; клиент считает по нему предпросмотр множителя |

`init` не розыгрывает RNG и не хранит истории: история раундов живёт на стороне
клиента как состояние сессии. Кроссраундового (`globalContext`) состояния у игры нет.

### Единицы измерения

Модель работает в **единицах броска** — целых `0..9999`. Клиент показывает игроку
проценты `0.00..99.99`, деля на 100. Пересчёт целиком на стороне клиента; в запросе
и ответе ходят только целые единицы броска.

Ставка `bet` и выплата `win` — в **младших единицах валюты**. Деноминацию задаёт
РГС, модель её не знает и не интерпретирует.

## 4. play

Запрос: `{ target, condition, bet }`. Ответ содержит `playData` со всеми полями из
`schema.json`.

Инварианты, за которые отвечает модель:

1. **Ровно один розыгрыш RNG на раунд** — `rng.getInt(0, 9999)`, вызывается один раз
   и всегда, независимо от исхода. Это критично: `verify()` обязан потреблять RNG
   идентично, иначе провабли-фэйр рассыпается.
2. `target` и `condition` возвращаются из запроса без изменений — клиенту нужен
   контекст для отрисовки, а реплею для восстановления раунда.
3. `multiplier` возвращается **всегда**, в том числе при проигрыше. Это множитель,
   который был бы применён при выигрыше, а не фактический коэффициент выплаты.
4. `win` при проигрыше строго `0`. При выигрыше `round(bet * multiplier)` —
   арифметическое округление, половина вверх.
5. `playData.win` дублирует `PlayResult.win`. Расхождение между ними — дефект.

### Границы `target` — единый источник

Границы порога задают **ручки** `target_min` / `target_max` действующего конфига, и
только они. Схема запроса эти границы числом **не дублирует**: два числа для одной
границы — два источника правды, и они расходятся (так и было: схема объявляла
`100..9900`, модель принимала `200..9800`).

Фактические границы клиент берёт из `initData.targetMin` / `initData.targetMax` —
это снимок действующих ручек. По ним и строится ползунок цели. Поле `target` в
схеме запроса несёт пометку `x-bounds` с именами управляющих ручек, чтобы источник
границы был машиночитаем.

Границы **включительно**: `target == target_min` и `target == target_max`
принимаются.

### Ошибки раунда

Модель отклоняет раунд исключением, если:

1. **запрос не проходит секцию `request` схемы модели** — неверный тип, нарушенный
   `minimum`, значение вне `enum`, отсутствующее обязательное поле, необъявленное
   лишнее поле (`additionalProperties: false`), нецелое там, где объявлен `integer`,
   а также целое вне безопасного диапазона double;
2. `target` вне `[target_min, target_max]` действующего конфига (границы —
   ручки, см. выше);
3. `condition` не равно `"over"` или `"under"`.

Все три случая — дефект **запроса**, класс исключения один: `RequestValidationError`
со списком всех нарушений сразу (полный перечень типов — §8). Голым `Error` они не
бросаются: рантайм отличает кривой запрос от сбоя математики по типу исключения.

Тихой коррекции значений нет: молча подставленный порог изменил бы математику
продукта, что §5.1 запрещает.

**Считать с мусорным входом запрещено.** До этой правки `bet = -100` принимался и
давал `win = -198` — отрицательную выплату в денежном контуре и `playData`, не
проходящий собственную схему модели. Действующее правило регламента:

> модель отклоняет любой запрос, не проходящий её схему; ответ модели обязан
> проходить её же схему всегда, включая ошибки.

Отказ выражается **исключением**, а не полем ответа: канонический
`@playtagon/model-sdk` не имеет канала ответа-ошибки — в `PlayResult` нет места под
ошибку, `playData` типизирован формой игры. Поэтому инвариант «ответ всегда валиден
по схеме» исполняется так: модель либо возвращает `PlayResult`, проходящий схему,
либо не возвращает ничего. Ответ-ошибка как отдельная объявленная форма требует
места в контракте SDK, которого сейчас нет (вопрос вынесен в отчёт).

Порядок операций: **валидация до розыгрыша**. Отвергнутый раунд не тратит ни одного
числа из буфера RNG — иначе провабли-фэйр следующего раунда сломался бы.

## 5. Граница `roll == target`

Проигрыш при обоих направлениях — условия строгие (`>` и `<`). Это не случайность
и не подлежит «исправлению»: именно этот случай формирует край дома сверх `rtp`.

Из-за него сумма вероятностей `over` и `under` при одном `target` меньше единицы:
`winChance(over) = (9999 - target) / 10000`, `winChance(under) = target / 10000`.
Их сумма равна `0.9999`, недостающая доля — ровно исход `roll == target`.

## 6. Провабли-фэйр и статус `roll`

Игра работает в режиме `rngMode: "fairness"`: РГС поставляет зафиксированный
детерминированный буфер RNG, вся случайность разыгрывается в первом и единственном
под-раунде, кроссраундовое состояние не хранится.

`verify()` заново выводит `roll` из того же буфера, потребляя RNG **идентично**
`play()` — ровно один `getInt(0, 9999)`. Совпадение `verifyData.roll` и
`playData.roll` того же раунда — обязательное свойство, покрытое тестом.

### `roll` — исход розыгрыша, а не ручка

`roll` объявлен **только** в секции `playData` схемы и в `knobs` не значится.
Это прямое следствие правила контракта «исход раунда — не ручка» (§1.5):

> Выпавшая грань, точка краша, вытянутая карта — это *результаты розыгрыша*: до
> раунда их не существует, после раунда клиент обязан их показать. Им не место в
> `knobs` — они объявляются в секции `playData` той же `schema.json` и раскрываются
> клиенту розыгрышем по определению. Ручка — вход математики; исход — её выход;
> `secret` применим только ко входам.

Прежняя редакция объявляла `roll` ручкой с `secret: true` и снимала противоречие
прозой в этом разделе. Проза противоречие не снимала: §2.1 ставит `schema.json`
выше `protocol.md`, а линт секретов (ворота 6) читает схему и загорался красным по
построению. Теперь противоречия нет и оговорка не нужна: ни одна ручка модели не
помечена секретной, а `playData.roll` — объявленный исход, который обязан
раскрываться, иначе игра не проверяема.

Расхождение с фикстурой дайса на devРГС (`fixture~dice/model/protocol.md`), где
`roll_result` объявлен ручкой и клиенту не уезжает, сохраняется и остаётся
осознанным: фикстура описывает другую игру — не провабли-фэйр, — и по действующей
редакции контракта её `roll_result` тоже не должен был бы лежать в `knobs`.

## 7. Чего у модели нет

- `roundContext` — всегда `null`, раунд атомарен;
- `globalContext` — всегда `null`, кроссраундового состояния нет (требование
  режима `fairness`);
- под-раундов, дополнительных ставок, бонусных режимов и типов раундов
  (`roundTypes` не объявлены — используется единственный тип по умолчанию).

## 8. Типы исключений модели

Обязательный раздел (требование штаба). Ошибки модели — типизированные
исключения (§1.5.1): секции ошибок в `PlayResult` не существует, рантайм
превращает исключение в стандартный ответ платформы. Узнавание — по `err.name`:
классы через границу бандла не переносятся, `instanceof` не работает.

| `err.name` | Кто бросает | Когда | Поля | Ответ рантайма* |
|---|---|---|---|---|
| `ConfigValidationError` | `createModel(values)` | `values` не проходят `knobs`: тип, диапазон, отсутствующая или необъявленная ручка, кросс-инварианты | `violations: string[]` — все нарушения сразу | 422 `MODEL_CONFIG_INVALID` |
| `RequestValidationError` | `play()`, до розыгрыша | запрос не проходит секцию `request` схемы; `target` вне границ ручек; `condition` вне `{over, under}` | `violations: string[]` — все нарушения сразу | 400 `MODEL_REQUEST_INVALID` |
| любое другое | — | сбой математики: модель в таком состоянии считать не имеет права | — | 500 `MODEL_PLAY_FAILED` / `MODEL_INIT_FAILED` |

\* Мапинг `err.name` → HTTP-ответ — конвенция исполняющего образа
(`generic-v1`), а не модели: модель отвечает только за тип и содержимое
исключения. Инвариант прежний: модель либо возвращает результат, проходящий
собственную схему, либо не возвращает ничего.

Оба типизированных исключения экспортируются из точки входа рядом с
`createModel`. Исключения из `init()` у этой модели невозможны по построению:
всё, что может отвергнуть подъём, отвергается фабрикой.
